# 记忆取回（memory-recall）设计方案

> 状态：**待确认执行**（方案定稿；用户已就触发阈值/默认开关/取回内容给出答复，见第六节）

> 功能全部完成后再按 `plan-template-enhanced` 的「文档两段式」改写成面向使用者的功能介绍。

## 一、修改目标

- **问题**：DSH 上下文被压缩（或重启后快照未加载）时，AI 丢失之前的对话记忆 → 重复提问、重复劳动、误解需求。
  用户原话在 1M 上下文里占比极小（可能总共没超过 3 句），却恰恰是**最不该丢**的部分。
- **期望效果**：自动检测「上下文疑似丢失」，把最近 **N 轮（默认 3，可配）** 的**用户原话** +
  **该轮 AI 的第一条回应（优先 reasoning）** 重新注入上下文，让 AI 立刻恢复状态。
- **成功标准**：压缩后下一回合，注入块出现在上下文里；AI 能直接引用注入的原话，不再重复询问已答过的问题。

## 二、潜在问题分析

| 风险类型 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| **误判**（用量正常波动被当成丢失） | 中 | 无谓注入、白烧 token | **阈值配置化、默认下降 ≥10%** 才触发；每次触发写日志可查 |
| **反馈环**（注入块本身被当成「用户消息」，越注越多） | 中 | 上下文反被撑爆 | 只认 `data.source.kind === "user"`；插件注入的 source 是 `plugin:dsh-session-conductor`（**已实测确认**两者在日志里可区分） |
| **注入过大**（刚压缩完又被塞满） | 中 | 与目的相悖 | 总长上限（默认 4000 字符）+ 每条上限（默认 800 字符） |
| **扫大日志耗时**（本机最大 49.2 MB / 15408 帧） | 中 | 该回合启动变慢 | 只在**检测到丢失**时才扫（罕见）；复用按帧流式读（常量内存，实测 heap 增量 24 MB）；带超时兜底 |
| 会话文件找不到 / 日志损坏 | 低 | 功能不生效 | 静默跳过 + 日志留痕，绝不阻断回合 |
| 与既有「每轮用量注入」叠加 | 低 | 两条注入消息 | 同一 hook、同一次注入**合并成一条**消息 |
| 兼容性破坏 | 低 | 旧版本行为变化 | 新增独立配置项；不改既有注入语义 |

**边界条件**（逐条给出行为）：

1. **首个回合**（无上一次用量）→ 不触发；
2. **用量读不到**（`sessionProjections` 未挂载）→ 不触发；
3. **全新会话**（一直 0 → 0）→ 不触发；
4. **重启后**（上次 50% → 本次 0%，快照未加载）→ **触发**（设计意图：把「快照没加载」也当失忆）；
5. **连续多条用户消息**（同一回合内）→ **合并成一条**；
6. **同一回合内**只注入一次（复用既有 turn 门控）；
7. **注入后用量回升** → 下一次比较自然不再触发（不会连环注）。

## 三、Skill 学习检查

| 检查项 | 结果 |
|---|---|
| 是否已有类似功能的 skill？ | **有** — `synology-webdav-and-skill-flatten`（zstd 帧流式读的方法论与「内存边界」章节）、本插件 `skills/dsh-session-conductor-functions.md` |
| 是否已有同类问题的解决方案？ | **有** — 1.2.2 的 `streamDecodedFrames` + `readColdSessionSummary`（同为「流式扫日志 + 只留需要的字段」） |
| 是否有官方推荐做法？ | **有** — 注入走官方 `agent/pre-step` + `createUserMessage`（logged 通道），不自己写会话日志 |
| 是否有现成库/工具？ | **有** — Node 自带 zstd、插件自带 `lib/zstd-frames.js`、`readContextUsage` |

**学到的关键点**：

1. **别造解码器**：`zstd-frames.js` 已在用 Node 自带 zstd（`createZstdDecompress`）；缺的只是「流式消费」，
   1.2.2 已补 `streamDecodedFrames`；
2. **注入必须走 logged 通道**且放**消息尾部**（前缀保持稳定 ⇒ prompt cache 仍命中）—— 1.1.1 的既有结论；
3. **日志里的事件类型（已实测）**：
   - `user/message`：`data.content[].text` + `data.source.kind`（实测值：`user` / `runtime-context` / `user-approval` / `model-selection`）；
   - `assistant/message`：`data.message.content[]`，首块常为 `{ type: "reasoning", text }`；
   - `agent/inbox/spliced`：**同一句话的重复副本**（要忽略，否则一轮会数成两条）；
   - `turn/start` / `turn/end`：回合边界（用于「同回合多条用户消息合并」）。

**决定复用**：`streamDecodedFrames` / `readContextUsage` / `createUserMessage` + `agent/pre-step` / `findSessionLogById`。
**决定不用**：自写 zstd 解码、自写注入通道、用 `agent/inbox/spliced` 当锚点（重复）。

## 五、逐文件改动详情

### 5.1 `lib/sessions/events.js` — 新增取回读取器

```js
/**
 * 取最近 N 轮「用户原话 + 该轮 AI 第一条回应」。
 * 复用按帧流式读：一遍扫完，只保留最近的 N 轮（常量内存）。
 * 锚点判定：只认 user/message 且 data.source.kind === "user"
 *   （排除插件注入 plugin:* 与 runtime-context / user-approval / model-selection）；
 * 同一回合内多条 user/message 合并成一轮；agent/inbox/spliced 是重复副本，忽略。
 */
export async function readRecentUserTurns(ctx, sessionId, { rounds = 3, maxCharsPerItem = 800, root } = {})
// 返回 [{ turn, time, userText, agentText }]，按时间正序（最早的在前）
```

### 5.2 `lib/features/memory-recall/index.js` — 新增

```js
/** 每会话记住上一次用量，用来判断「这次比上次少」= 上下文疑似丢失。 */
const lastUsageBySession = new WeakMap();

/** 检测：本次已用量比上次明显下降（阈值配置化，默认 10%）→ 判定为「上下文疑似丢失」。 */
export function detectContextLoss(prev, current, { minDropRatio = 0.10, minDropTokens = 0 })

/** 组装注入文本（标题 + 每轮两块；总长与每条都有上限）。 */
export function formatRecallBlock(turns, { prevPercent, currentPercent, maxTotalChars = 4000 })

/** 主入口：检测 → 取回 → 组装；任何一步失败都静默返回 null（不阻断回合）。 */
export async function buildMemoryRecall(ctx, agent, usageSnapshot, opts)
```

注入文本形态（示例）：

```
【记忆取回】检测到上下文用量下降（上次 62% → 本次 18%），判断上下文可能已丢失（压缩或快照未加载）。
以下是你最近 3 轮对话的用户原话与你的首个回应，供你恢复上下文：

— 第 1 轮（10-15 16:42）—
用户：把本 dsh 的插件重新安装回去
你（当时的第一反应）：我先确认当前安装状态与 profile 布局……

— 第 2 轮（10-15 17:05）—
用户：……
你（当时的第一反应）：……
```

### 5.3 `lib/apply.js` — 接线

在**既有**的用量注入 hook（同一个 `agent/pre-step`）内：

1. 读用量快照（已有逻辑）→ 与上一次比较 → 判定是否丢失；
2. 若丢失 → `buildMemoryRecall(...)` → 把「用量行 + 记忆取回块」**拼成一条** user 消息注入（尾部）；
3. 更新 `lastUsageBySession`。

### 5.4 `lib/core/config.js` — 配置项

```js
retrieveMemory: true,               // 记忆取回总开关（默认开）
retrieveMemoryRounds: 3,            // 取回最近几轮
retrieveMemoryMinDropRatio: 0.10,   // 触发阈值：下降比例（默认 10%，配置化）
retrieveMemoryMinDropTokens: 0,     // 触发阈值：下降绝对量（默认不限）
retrieveMemoryMaxChars: 4000,       // 注入总长上限
retrieveMemoryMaxCharsPerItem: 800, // 单条（原话 / 回应）上限
```

## 七、影响分析

| 维度 | 影响 | 说明 |
|---|---|---|
| 现有功能 | **低** | 新增独立模块；只在检测到丢失时多注入一段文本 |
| 性能 | **低** | 每回合多一次 O(1) 用量比较；扫描只在触发时发生（罕见，且常量内存） |
| 兼容性 | **低** | 新配置项可关；不改既有注入语义与工具面 |
| 安全性 | **低** | 内容全部来自本会话自己的日志，不外发、不落新文件 |
| 可维护性 | **低** | 检测/取回/组装三段纯函数，可单测；取回读取器复用既有按帧读 |
