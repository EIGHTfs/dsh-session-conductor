# 记忆取回（memory-recall）

> 版本：1.3.0 ｜ 状态：**已实现并验证通过**
> 本文档按 `plan-template-enhanced` 的「文档两段式」撰写：**上半是面向使用者的功能介绍**，
> 设计细节（风险表 / 文件清单 / 逐文件改动 / 看板）收在**附录**，供维护者查阅。

---

## 一、它解决什么问题

DSH 的上下文会被**压缩**；实例重启后快照也可能**尚未加载完**。这两种情况下 AI 会「失忆」：
重复问你已经答过的问题、重复做已经做过的事、甚至误解你的需求。

而你的话在整个上下文里占比极小 —— 1M 上下文里可能总共没超过 3 句 —— 却恰恰是**最不该丢**的部分。

**记忆取回**做的就是：检测到「上下文疑似丢失」时，把最近几轮的**你的原话** +
**AI 当时的第一条回应**重新塞回上下文，让 AI 立刻接上之前的状态。

## 二、怎么用

### 2.1 自动（默认开，装了就生效）

每回合插件会比较「本次上下文已用量」与「上次」：

- 本次比上次**下降 10% 以上**（默认阈值，可配）⇒ 判定为「上下文疑似丢失」；
- 此时自动把最近 **3 轮**（可配）取回来，和每轮的用量提示**合并成一条**注入到消息尾部。

为什么用「用量下降」而不是「监测压缩」：用量下降能覆盖**所有**失去上下文的形态 ——
压缩只是最常见的一种；重启后快照没加载时用量会掉到 0，那同样该按失忆处理。

### 2.2 手动（AI 工具 `recall_memory`）

AI 也可以自己按需回溯，比如它想确认「你最初是怎么说的」：

```
recall_memory({ rounds: 5 })   // 取最近 5 轮；不传则用配置里的默认值，上限 50
```

只读：只把取回的文本返回给 AI，不会自动改上下文。

### 2.3 取回的内容长什么样

```
【记忆取回】检测到上下文用量下降（上次 62% → 本次 18%），判断上下文可能已丢失（压缩，或实例重启后快照尚未加载）。
以下是你最近 3 轮的用户消息文本与你的首个回应，供你恢复上下文：

— 第 1 轮（10-15 16:42） —
用户消息：把本 dsh 的插件重新安装回去
你（当时的第一反应）：我先确认当前安装状态与 profile 布局……

— 第 2 轮（10-15 17:05） —
用户消息：……
你（当时的第一反应）：……
```

**为什么取这两样**：

- **你的原话** —— 占比小但信息密度最高，是恢复上下文的支点；
- **AI 的第一条回应**（优先取当时的**思考**，没有才取正文）—— 那是「当时」对你这句话的理解，
  直接把结论还给它，省得它重新推测。

## 三、效果

- 压缩 / 重启后，AI 下一回合就能看到你最近说过什么、它当时怎么理解的；
- 取回是**只读扫日志**，不改任何会话数据；
- 实测开销：取 3 轮 ≈ **27 ms**，内存增量 ≈ **6 MB**（按 zstd 帧流式读，与日志大小无关）。

## 四、边界与限制（如实说明）

| 情况 | 行为 |
|---|---|
| 首个回合（还没有「上次用量」） | 不触发 |
| 用量读不到（投影服务未挂载） | 不触发 |
| 全新会话（一直是 0） | 不触发 |
| 实例重启后用量掉到 0 | **触发**（这是设计意图，按失忆处理） |
| 同一个回合里你连发好几条 | **合并成一轮**，不会数成好几轮 |
| 日志文件找不到 / 损坏 | 静默跳过（只留一行日志），**绝不阻断回合** |
| 刚压缩完、上下文很紧 | 注入总长上限 4000 字符、单条 800 字符；超限时**丢最早的轮次**，保留最近的 |
| 插件自己注入的内容 | **不会被取回**（只认真正的用户消息，避免越注越多） |

## 五、配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `retrieveMemory` | `true` | 总开关（关掉即只剩手动工具） |
| `retrieveMemoryRounds` | `3` | 取回最近几轮 |
| `retrieveMemoryMinDropRatio` | `0.10` | 触发阈值：用量下降比例 |
| `retrieveMemoryMinDropTokens` | `0` | 触发阈值：下降绝对量（0 = 不限，两者满足其一即触发） |
| `retrieveMemoryMaxChars` | `4000` | 注入总长上限 |
| `retrieveMemoryMaxCharsPerItem` | `800` | 单条（你的原话 / AI 首条回应）上限 |

## A2. 关键正确性约束（改之前必读）

1. **锚点只认 `user/message` 且 `data.source.kind === "user"`** —— 必须排除插件自身注入
   （`plugin:dsh-session-conductor`）与 `runtime-context`，否则注入块会被下一轮取回，形成越注越多的反馈环；
2. **忽略 `agent/inbox/spliced`** —— 它是同一句话的投递副本（实测同一句话先出现在 spliced、后出现在 user/message），
   用它会把一轮数成两条；
3. **同回合内**（其间无 `turn/end`）连续多条用户消息**合并成一轮**；
4. **无论是否触发都记账**（`noteUsage`）—— 否则读取失败时每个回合都会反复触发；
5. **任何一步失败都静默返回 null**，绝不阻断回合。

## A3. 复用与取舍

- **复用**：`streamDecodedFrames`（1.2.2 新增的按帧流式消费）、`readContextUsage`、
  官方 `createUserMessage` + `agent/pre-step`、`findSessionLogById`；
- **不新造**：不写 zstd 解码器（插件 `lib/zstd-frames.js` 已在用 Node 自带 zstd）、
  不新造注入通道、不用 `agent/inbox/spliced` 当锚点。

## A4. 风险与缓解（设计期评估）

| 风险 | 缓解 |
|---|---|
| 误判（用量正常波动被当成丢失） | 阈值配置化（默认 10%）+ 每次触发写日志可查 |
| 反馈环 | 只认 `source.kind === "user"`（已实测两种 source 在日志里可区分） |
| 注入过大 | 总长 / 单条双上限，超限丢最早的轮次 |
| 扫大日志耗时 | 只在触发时扫一次；按帧流式读（常量内存）；带超时兜底 |
| 与用量注入叠加 | 同一 hook 内合并成一条消息 |
