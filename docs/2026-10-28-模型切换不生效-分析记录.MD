# 模型切换不生效（官方 UI 切换后请求仍走旧 provider）— 分析记录

> 状态：**已解决**（2026-10-28 00:39 实测确认）。
>
> **真因（结论）**：本插件（dsh-session-conductor）自己的 `memberModelOverrides` 把这个会话钉死成 `ccc`，
> 它通过 `agent/request` waterfall 强制改写请求配置，**优先级高于官方 selection** —— 所以
> 界面切、改日志、重启全部无效。修复 = 用 `set_member_model` 把 override 改成目标模型，**立即生效、无需重启**。
> 详见第十一节「最终定案」。
>
> **注意**：第四、五节记录的「`current` / `assembled` 依赖顺序缺陷」与「改 request/header」都是**排查过程中的
> 干扰项，并非真因**（那些机制确实存在，但在本例中不是阻塞点）。保留它们是因为取证路径可复用。
> 本插件 override 的优先级语义缺陷仍待修（见第十一节末），否则同类问题会再犯。

## 一、现象

用户在主会话界面用**官方模型选择器**切换模型后：

- 界面/日志里的 `model/selection` 事件确实变成了目标模型
- 但该会话后续**所有请求**仍然发往**旧的 provider**
- 旧 provider（`ccc`）的密钥已失效，于是报 `API 密钥无效`

涉及会话：`session-611c23a5-5735-46ca-9f9c-afd2774e9a65`

该会话特征：

| 字段 | 值 | 备注 |
|---|---|---|
| `delegationDepth` | `0` | 身份上是主会话，界面**有**模型选择器（`ui-model-selection` 只对 addressed subagent 禁用） |
| `parentSession` | `session-27226077-...` | 有父会话 |
| `isSeeded` | `true` | 从父会话 seed 而来 |
| `agentPreset` | `standard` | — |
| 事件总数 | 65513 | 长历史 |
| `subagent/model-selection-policy` | seq 3：`{"allowedModels":[{"provider":"agnes","model":"agnes-3.0-flash"}]}` | **可疑因素①**：子代理模型白名单 |

### 3.2 `selectForNextRequest` 就是写 selection 事件的地方

`api/session-controller/lib/index.js:321`：

## 四、【干扰项，非真因】`current` 与 `assembled` 的依赖顺序

后续继续读代码，把第三节的三条线索串起来，根因已定位（原「三个可疑因素」见第五节，均不是主因）。

`core/agent/lib/index.js:166` — `installModelSelection(agentCtx, selection)` 注册了三个钩子：

```js
// ① 组装 system prompt 时：把 selection.current 快照进 selection.assembled
const disposeAssembly = agentCtx.on("system-prompt/assemble", async (_a, _c, next) => {
  const selected = selection.current;
  const assembled = await next();
  selection.assembled = selected;        // ← assembled 只在这里被赋值
  if (selected === void 0) return assembled;
  return { ...assembled, variables: { ...assembled.variables, provider: selected.provider, model: selected.model } };
});

// ② 发请求时：读的是 assembled，不是 current！
const disposeRequest = agentCtx.on("agent/request", async (_p, next) => {
  const resolved = await next();
  const selected = selection.assembled;              // ← 关键
  if (selected === void 0) return resolved;          // ← undefined 就原样返回（= 用原配置）
  return { ...withoutInheritedEffort, provider: selected.provider, model: selected.model };
});
```

**问题链条**：

1. 用户 UI 切换 → `selectModel` → `selectForNextRequest` → 写 `model/selection` 事件 ✔ + `selection.current = 新值`（setter 存在，赋值有效）✔
2. 但**请求组装读的是 `selection.assembled`**，它只在 `system-prompt/assemble` 钩子里被赋值
3. 若该会话的 system prompt 被**缓存复用、没有重新 assemble**，`assembled` 就一直是 `undefined`
4. `assembled === undefined` → `agent/request` 钩子直接 `return resolved`（不覆盖）→ 请求沿用 `seedConfig`
5. `seedConfig` 来自 `core/agent-loop/lib/index.js:1186`：`requestHeaderLogged ? requestProposal(persistedHeader)`，即**最后一条 `request/header` 的 config**
6. 而最后一条 `request/header` 是 `ccc` → **自我锁定**：一旦某次请求走了 ccc，后续就永远用 ccc

这也解释了为什么「切三次、跨三个回合」全都无效 —— 每次都没触发重新 assemble。

**定性**：这是宿主侧的依赖顺序缺陷（切换写 `current`，消费读 `assembled`，两者只在 assemble 时同步），
不是本插件的 bug，也不是配置写错。插件这条链路（`set_member_model`）写的是同一类 `model/selection` 事件，
同样依赖 `assembled` 的同步，所以也会受同一问题影响。

**新得出的两条约束**：

1. `core/session/lib/index.js:1610` — `requestHeader()` 是 `foldRequestHeader` 折叠（简单取最后一条），所以「改最后一条」这个做法本身没问题。
2. `core/agent-loop/lib/index.js:1186` — seedConfig 有分支：`this.requestHeaderLogged ? requestProposal(persistedHeader) : { ...route }`。
   **`requestHeaderLogged` 是 agent 实例的内存标志**；新 resume 的 agent 为 `false` → 走 `route` 分支，
   `route = { provider: this.options.provider, model: this.options.model }`，**完全不读日志里的 header**。
   → 所以「改日志」对 live/刚 resume 的 agent 无效，必须让进程重新构造 agent。

**结论**：剩余阻碍是**进程内状态**（AgentOptions / 投影 pending / selection 缓存三者之一），
不是磁盘数据。要彻底生效需**重启宿主**，让 agent 按改过的日志重建。
在重启前，任何「唤醒该会话」的动作都会继续用 ccc。

## 十一、最终定案（2026-10-28 00:39 实测通过）

### 真因

本插件的持久化 override 把这个会话的模型钉死了：

`.dsh/storages/dsh_session_conductor.json` → `memberModelOverrides`：

```json
"session-611c23a5-5735-46ca-9f9c-afd2774e9a65": { "provider": "ccc", "model": "deepseek-v4.1-flash" },
"c9a6a72c-...": { "provider": "ccc", "model": "deepseek-v4.1-flash" },
"session-f7cd2e12-...": { "provider": "ccc", "model": "deepseek-v4.1-flash" }
```

这些记录是 2026-10-27 01:36 一次批量 `set_member_model({})`（三参数全空 = 全部成员跟随主代理）写下的，
当时主代理自己就是 `ccc`，于是三个成员被钉成 `ccc`。

插件的 `agent/request` waterfall（`lib/features/member-model/override.js`）会在每次请求组装时
**强制把配置改写成 override 里的值**，其优先级高于：
- 官方 `selectModel` 写的 `selection.current` / `selection.assembled`
- 会话日志里的 `request/header` 与 `request/context`
- 宿主重启（override 存在 json 里，重启后照样加载）

所以「界面切三次、跨三个回合、改日志、重启」全部无效 —— 唯一有效的入口是改 override 本身。

### 修复动作（无需重启，立即生效）

```js
set_member_model({ target: "session-611c23a5-5735-46ca-9f9c-afd2774e9a65",
                   provider: "sa6400", model: "cn:deepseek-v4.1-flash" })
```

- override 存储随即变为 `sa6400/cn:deepseek-v4.1-flash`
- 唤醒该会话后实测：`seq 65630 REQ-HDR sa6400/cn:deepseek-v4.1-flash` ✅

### 排查过程中被证伪的方向（别再走这条路）

| 方向 | 证伪依据 |
|---|---|
| 官方 `current` / `assembled` 依赖顺序缺陷 | 投影缓存里 `pending = sa6400`（官方切换已生效），但请求仍走 ccc ⇒ 有更高优先级的覆盖者 |
| 改会话日志里的 `request/header` / `request/context` | 改完被 override 覆盖；且唤醒后又写下新的 ccc 记录 |
| 投影缓存 `session_projcache` 陈旧 | 缓存里 `lastUsed=ccc`、`pending=sa6400`，与日志一致，不是矛盾源 |
| 子代理模型白名单 `subagent/model-selection-policy` | 只用于设置面板与 spawn 侧，主会话请求不读它 |
| 重启宿主 | override 持久化在 json 里，重启后照旧加载 |

### 插件待修（同一坑会再犯）

**语义缺陷**：override 一旦写入就永久压过用户在官方界面的选择，且用户完全无从察觉
（界面显示的是自己选的新模型，实际请求用的是 override 里的旧模型）。

建议修法（择一或组合）：

1. **官方切换即清除 override**：监听 `model/selection` 事件的本会话变更，若来源不是本插件则删除对应 override；
2. **override 带溯源与时效**：记录 `source`（plugin/user）与写入时间，官方切换后自动失效或降级为提示；
3. **回执明确告警**：`set_member_model` 的结果里显式标注「已设置持久 override，会覆盖界面选择，清除方式：…」；
4. **提供清除入口**：工具/指令支持 `clearOverride`（如 `set_member_model({target, provider:"", model:""})`）。

在修好之前，**使用注意**：`set_member_model` 的批量「跟随主代理」写入的是**当时**主代理的模型，
之后主代理再换模型，这些成员不会跟着变，且界面切换对它们无效。
