| 1.3.7 | **修「刚重启时面板报读取会话列表失败、过一会儿又自己好了」**。两个原因叠在一起：① 面板给列表请求套了 **30 秒 fetch 超时**，而冷缓存首次构建要逐份解压上百份日志（本机实测 41~226 秒）—— 慢但正常的请求被 30 秒准时掐断，报成网络失败；② 重启瞬间插件路由/宿主服务未必已就绪，首次请求直接网络失败，而面板**只有手动「重试」**，不点就一直停在错误态。改法：流式列表请求**不再设超时**（流式接口的正确判据是「有没有在吐数据」，不是「多久回完」；`__scFetch` 第三个参数传 0 即关闭超时，默认仍是 30 秒，其余接口行为不变）；服务端写出 NDJSON 头行后**立即 flush**，浏览器不再干等；面板失败后按 3s / 8s / 20s / 45s **自动退避重试**，界面给出「N 秒后自动重试」倒计时，成功一次即清零，组件卸载时清掉定时器（不会在面板关闭后继续打后端）。新增 i18n `list.autoRetry`（中英各一条） |
| 1.3.6 | **四个缺陷一起修：记忆取回轮数被吃掉、输出不给代价、面板点会话进不去、会话 id 复制麻烦**。① **`recall_memory` 要 30 轮只回 5 轮**：读侧没截断（`readRecentUserTurns` 的 `shift()` 只保留最后 N 轮，参数本身是生效的），真凶在**输出侧总长上限**——手动取回沿用自动注入的 `retrieveMemoryMaxChars`（默认 4000 字符），超限时从**最早一轮开始丢**，且**一个字都不提**，于是现象看起来像「轮数参数没生效」。现在手动通道按 `rounds × retrieveMemoryMaxCharsPerItem`（默认 800）算总长预算，并在真的被截断时明说「受总长上限 N 字符限制，最早的 K 轮未包含；需要更早的内容请调小 rounds 分次取」。② **输出末尾附 `（本次输出正文 N 字符）`**：取回代价一眼可见，也顺带成为「有没有被截断」的自证。③ **面板点会话进不去**：原实现走 `ctx.get("sessions").open(...)`，而宿主客户端**没有 `sessions` 服务**，可选链把「服务不存在」吞成静默无反应——不报错所以一直没被发现。现在按 `workspaceNavigation.openSession` → `uiWorkspace.openSession` → 旧版 `sessions.open` **三级回退**（旧宿主照样可用，新宿主走官方入口），三级都不存在才 `console.warn` 留痕，不再静默。④ 面板里的会话 id 改为**单击复制**（优先 Clipboard API，非安全上下文退回 `execCommand`），复制成功该行短暂显示 `✅ 已复制` 再复原，不依赖宿主 toast（旧版未必有）。新增两条回归测试（30 轮必须全取回、被截断必须给出提示），全量单测 26 个文件全绿 |
