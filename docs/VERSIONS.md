## 版本列表

| 版本 | 内容 |
|------|------|
| 1.1.0 | 新增**跨会话消息**与**指定模型新建会话**三个 AI 工具（AI 可直接 toolcall）：`list_sessions`（列出会话：id/标题/工作区/状态/最后活动/是否当前会话）、`send_to_session`（给指定会话投递消息，目标空闲时由本体自动唤醒）、`create_session`（新建会话，可指定 provider/model，可选带初始消息）。实现要点：**全部走本体官方 API**（`sessionController` 的 `@Remote('create')` / `@Remote('selectModel')` / `@Remote('prompt')`）——`prompt` 受理前会先 resume 目标会话，唤醒与幂等（requestId）都由本体保证；**不自己写会话日志**（inbox 家族只有 `agent/inbox/spliced` 落盘，其 fold 对非法 splice 直接抛错，自己写等于拿对方会话完整性冒险）。安全硬约束：禁自投、协作链跳数 ≥3 拒绝、同一对会话 60s 内最多 5 条、requestId 幂等与在途去重；`create_session` 对「会话已建但模型未设/初始消息未投」如实回执不谎报成功。新增单测 23 条 |
| 1.0.11 | 修**方案门禁锚点写死章节号**导致的「开启强制门禁后所有编辑被永久拒绝」：门禁锚点原为字面量 `八、是否执行`，而模板把「是否执行」从第八节移到第十一节后两者脱节——**AI 照模板写方案也过不了锚点**，deny 文案又不提示锚点不匹配。改为**语义锚点**：标题锚点（`修改方案提案` / `门禁表`）+ 确认段锚点（`是否执行` / `请回复确认` / `确认或修改方案` / `等待…确认` 正则），任一命中即成立，**均不含章节号**；同步修掉 deny 文案里的同一处写死与 skill 文档描述。新增 4 条回归护栏（核心一条：章节号变了仍认提案），门禁单测 38/38、全量 unit 18/18 通过 |
| 1.0.10 | 修「按 v3 开发、未适配 DSH 0.2.1 的 v4 会话格式」导致的校验误判：v4 把 `tool/result` 的 `message.role` 从 `user` 改为 `tool`（first-class tool-role——`toolCallId` 提升到 message 层、content 不再有 `tool-result` wrapper）。原校验写死 `role === "user"`，使**全部 v4 会话**被判「role 应为 user」；凡「写回前先校验」的路径必然失败（如 `set_member_model` 对未挂载成员写 `model/selection` 事件时报「写入后校验失败」）。改为按 role 分派，两种形态各按官方口径校验（v4 对齐 `assertV4ToolResultMessage`）。真实数据验证：v4 30/30 通过（修复前全失败）、v3 10/10 通过（回归）；新增单测 11 条 |
| 1.0.9 | 修 dsh-session-conductor 四处「引用未定义标识符 / 状态未水合」导致的**静默失效**（同一家族，全部被 try/catch 吞成一行日志）：① 收尾汇报约定的系统提示词段 `task-completion-report`（order 1000）因 `text: TASK_COMPLETION_CONVENTION` 引用的常量**自 1.0.0 起从未定义**，构造参数时抛 `ReferenceError` ⇒ 该段从未注册；改为同步读取插件自带权威文本 `skills/task-completion-report.md`（去 frontmatter）。② 方案/收尾模板的上下文注入（`agent/pre-step`）因 `collectTemplateSlotText` 未导入而每次抛错 ⇒ 从未注入过。③ 方案模板强制门禁因 `planGateAllows` / `PLAN_ENFORCE_EDIT_TOOLS` / `PLAN_ENFORCE_BASH_WRITE_RE` / `planEnforceDenyMessage` 未导入而恒走 fail-open 放行 ⇒ 设置里开着也从未拦过一次；②③六处缺失一次性补齐：`collectTemplateSlotText` / `planGateAllows` / `PLAN_ENFORCE_EDIT_TOOLS` / `PLAN_ENFORCE_BASH_WRITE_RE` / `planEnforceDenyMessage` 补导入；非 dryRun 的双格式修复原为未导入的裸调用 `repairDualFormatSessions(...)`（恒抛 ReferenceError 被 catch 成 400「repair-dual-format-failed」⇒ 该修复从未执行过），改为与 scan 同源的懒加载命名空间调用。④ `templateStateCache` 初值为 `TEMPLATE_DEFAULTS`（全关）且只被 `/templates` 路由覆写 ⇒ 宿主重启后未打开过设置页时模板不注入、门禁不生效；新增启动水合 `hydrateTemplateState()`（两个消费点前读取存储状态）。⑤ `createUserMessage`（宿主包 `@deepseek-ai/dsh-llm`）未导入 ⇒ 改为带守卫的动态导入，缺包时跳过并留痕。验证：运行时探针（假 ctx 驱动安装副本的真 `apply()`）实测系统提示词段注册 1 段/文本 1023 字、`pre-step` 注入 1 条含「门禁表」方案模板、`enforce` 下 `edit` 调用返回 deny；单测 17/17 通过，新增回归护栏（约定文本可读、接线绑定已解析文本、lib 无未定义标识符引用、启动水合调用点 ≥2、跨模块导出-引用扫描为 0） |
