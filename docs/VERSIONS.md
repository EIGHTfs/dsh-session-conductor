| 1.3.0 | **新增「记忆取回」**：检测到上下文用量**明显下降**（默认 ≥10%，可配）即判定「上下文疑似丢失」——压缩、截断、实例重启后快照未加载**都算**（比只盯压缩覆盖更全），此时自动把最近 **3 轮（可配）** 的**用户原话 + 该轮 AI 的第一条回应**（优先取当时的 reasoning）重新注入，让 AI 立刻恢复状态。**设计要点**：① 以**用户消息为锚**（原话在上下文里占比极小却最重要，1M 上下文可能总共没超过 3 句）；② 要 **AI 的第一条回应**（那是「当时」对原话的理解，直接给结论省得重新推测）；③ **同回合连发合并成一轮**；④ **只认 `source.kind === "user"`**（排除插件自身注入与 runtime-context，否则注入块会被下一轮取回形成反馈环）；⑤ 按 zstd 帧**流式**读日志（常量内存，实测 3 轮 27 ms / heap 6.1 MB）；⑥ 注入与「每轮用量注入」**合并成同一条消息**（尾部注入，prompt cache 友好）；⑦ 总长 4000 / 单条 800 字符上限（刚压缩完的上下文不该再被塞满）；⑧ 任何一步失败都静默跳过，绝不阻断回合。配置项 `retrieveMemory` / `retrieveMemoryRounds` / `retrieveMemoryMinDropRatio` / `retrieveMemoryMinDropTokens` / `retrieveMemoryMaxChars` / `retrieveMemoryMaxCharsPerItem`（默认开）。**另提供 AI 工具 `recall_memory`**：让 AI 自己按需回溯（自动注入之外的手动通道），参数 `rounds` = 取几轮（默认取配置 `retrieveMemoryRounds`，上限 50），只读返回文本、不改上下文。新增 `test/unit/test-memory-recall.mjs`（16 条：阈值边界/合并/上限/反馈环排除/降级/工具注册与参数夹取）。方案文档 `docs/2026-10-15-记忆取回.MD` |
| 1.2.2 | **冷会话读日志改「按 zstd 帧流式读」——把单会话内存从数百 MB 压到常量级**。① 新增 `streamDecodedFrames(buf, onChunk)`（`lib/zstd-frames.js`）：逐帧解压、**把解压分片直接交给消费者，不拼接不驻留** —— 原 `decodeAllFrames` 会把所有帧拼成一个大字符串，大日志下峰值就是整份文本。仍坚持逐帧喂解压器（整体流式会丢后续帧）。② 新增 `readColdSessionSummary()`（`lib/sessions/events.js`）：直接定位并读取日志文件（`findSessionLogById`，复用 `session-log.js` 的命名兼容），流式解压 + `StringDecoder` 增量切行 + 逐行 `JSON.parse`，只累加列表真正需要的三个值（最后一条 `session/title`、最后一条事件的 `time`、最后一个 `turn/end` 的 reason）并保留有界尾部（默认 2000 条，供官方 `interruptedTurnClosers` 判定开放回合）；找不到文件时**回退**到原 handle 读法。③ `list.js` 冷会话解析改走摘要读。**实测**：本机最大日志（2 帧 / 23585 事件）**heap 增量 24.1 MB、峰值 29.2 MB**（原路径要把 173 MB 解压文本变成事件对象数组）；与「全量解码 + `lastEventTime`/`hasOpenTurn`/`interruptionInfo`」朴素计算**逐项对拍一致**（含合成的中断闭合器与事件总数）。④ 新增 `test/unit/test-cold-session-read.mjs`（10 条：用 `zstdCompress` 造**真实多帧**夹具端到端验证，不 mock 解压；含「list.js 必须优先摘要读且保留回退」护栏）。⑤ `test/api/test-readonly-api.mjs` 的 `/list` 用例单独放宽预算并写明「耗时取决于实例规模与负载」——该端点是重活，不应把「实例正忙」判成「接口坏了」。单测 21 个文件全绿 |

| 1.2.0 | **修掉会话列表的「缓存永不生效」+ 内存/超时压力**（线上实测：进程 RSS 2.33 GB、峰值 2.75 GB（堆上限 3.19 GB），`GET /list` >120s 无响应）。**根因**：宿主 `sessionPersistence.list()` 现在返回的是 `SessionPersistenceSnapshot`（`{ header, revision, eventCount?, sizeBytes? }`），而插件先探测早已不存在的 `listSnapshots()`、探测失败后退回「把 list() 的返回值当裸 header 用」并把 `revision` 置 null —— **revision 为 null 的条目永不进磁盘缓存**，于是每次列表构建都要把 164 个会话 / 1.5 GB 日志全量重解析（实测单份日志 49.2 MB 压缩 → **173.3 MB 解压**，膨胀 3.2~5.0×）。**修法**：统一按快照解析（`entry.header ?? entry` 兼容旧裸 header）并带上 `revision`，缓存恢复正常 ⇒ 同一会话只在日志变更时解析一次。**同时**：`list_sessions` 输出收敛（`query` 子串过滤 + `limit`/`offset` 分页，默认只给 20 条，避免整表塞进调用方上下文）。**另记录一次被推翻的优化**：曾把冷会话读改成「分块 `read(offset, chunk)`」以省内存，实测发现宿主 `readCurrent` 每次都会 `readStoredLog(path)` 全量解压、`offset/length` 只是内存数组切片 ⇒ 分块读**内存峰值不变、耗时变 O(n²)**（api 门禁里 `/list` 直接超时），已撤回并在 `events.js` 写明该限制与「真正可行的路子是绕过 handle 按 zstd 帧解码」。顺带：`events.js` 的宿主包改懒加载（该文件因此可被单测覆盖，新增 7 条冷会话读回归 + 2 条「禁止改回分块读」护栏）；单测 21 个文件全绿 |
