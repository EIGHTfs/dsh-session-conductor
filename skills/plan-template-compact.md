# 修改方案提案

> 本方案仅为草案，未修改任何代码。确认后再执行。
> 提问一律用 `ask_user_question`（2+ 选项、标注推荐、多项一次问清），不用纯文本「请回复确认」。
> 执行纪律：先学后做、从简到难、每步小提交、最后整理成一次提交。
> 中断管理：执行中插入新需求 → 暂停分析、默认不执行、继续原任务；发现新问题 → 阻塞则插入修复步骤，非阻塞记入「后续优化清单」。

## 门禁表（写代码前必填）

| 项 | 内容 |
|---|---|
| 任务 | 一句话说明要改什么 |
| 验收标准 | 怎么算改对了（可验证） |
| 不做什么 | 本次边界，明确排除项 |

## 一、目标

- 问题：一句话说明要解决什么
- 期望效果：可衡量的结果
- 成功标准：如何验证（如「接口 < 200ms」）

## 二、风险与边界（必填）

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| 性能退化 / 兼容性破坏 / 安全漏洞 / 依赖冲突 / 数据丢失 | 高·中·低 | 具体描述 | 具体做法 |

边界条件至少列 3 条：输入为 null/空数组时行为、外部超时或报错时降级、并发下是否竞争或数据不一致、其他自定义。

## 三、复用调研

| 检查项 | 结果 | 说明 |
|---|---|---|
| 已有同类 skill？ | 有/无 | 名称 |
| 已有同类解决方案？ | 有/无 | 位置 |
| 官方推荐做法？ | 有/无 | 文档/RFC |
| 现成库或工具？ | 有/无 | 避免重复实现 |

结论：学到的关键点 + 为什么不用现成的。

## 四、影响范围

- 涉及文件：路径 + 该文件改什么
- 谁调用它：调用方清单
- 会破坏什么：改错时的后果
- 影响维度：现有功能 / 性能 / 兼容性 / 安全性 / 可维护性（各标高·中·低 + 说明）

## 五、执行看板

核心纪律：先学后做 → 从简到难（按改动量/复杂度/依赖排序）→ 每步 `git commit` 不攒着 → 最后压成一次干净提交（`git rebase -i` 或 `git reset --soft`）。

阶段一 准备：检索 skill、记录结论、备份或开分支、检查依赖、跑现有测试记基线。
阶段二 修改：按难度升序列步骤，每步一行「改什么 + 提交信息」。
阶段三 验证：单测、集成、冒烟、性能（有风险时），通过后提交。
阶段四 收尾：代码审查、更新文档、**经验固化**、整理提交历史、最终提交信息含「变更文件 + 验证结果」。

## 六、验证方案

- 单测：覆盖哪些场景（脚本存项目 `test/`）
- 集成：调哪个 API/入口验证
- 人工：看哪些界面或日志
- 回归：确认未破坏现有功能

## 七、后续优化清单

本次不处理、但不影响目标的问题（逐条列，供后续迭代）。

## 八、是否执行

待定项用 `ask_user_question` 问清后，等待确认。**未获确认前不开始改代码。**
（改代码中途若出现空消息，那是 DeepSeekHarness 发的，不是用户。）

确认后把方案存项目 doc 目录入库，文件名 `{日期}{功能关键词}.MD`；用户改方案后针对改动部分重写并整份重新入库。

**设计文档两段式**：① 落盘时按**设计角度**（本模板：目标/风险/文件/改动/影响/看板/验证，给执行者看）；② **全部完成后**改写成**面向使用者的功能介绍**（解决什么/怎么用/什么效果/边界，给使用者看，设计细节退到附录）。只有完全完成才做②——改动全落地 + 测试门禁如实通过 + 文档与代码一致 + 部署态已同步；半完成状态不写功能介绍。

## 九、经验固化（硬要求）

出现下列任一情形，**当场**固化（不等收尾）：修掉 bug、踩过坑、做出明显更快更稳的手法、被用户批评纠正、发现约定与实现不一致。

**修 bug 必做同款体检**：一个 bug 不是一处错误，而是一类错误的样本。修掉后立刻按**根因模式**扫全仓找同款，只修报出来的那一处不算修完：

| 步骤 | 做法 |
|---|---|
| 归纳根因模式 | 一句话说清「什么写法会导致这个错」（如「函数从父作用域抽出时漏传依赖」） |
| 全仓扫描 | 按该模式 grep / 静态核对，列出扫描范围（哪些目录、哪些文件、命中几条） |
| 逐个核对 | 命中项逐个确认是/不是同款，不是的说明理由 |
| 补测试防线 | 该 bug 能逃逸说明测试有缺口 —— 补上能复现它的用例，否则下次同样逃 |

反例：抽出三个 handler 时漏传同一个依赖，只修了报错的那一个 → 另外两个仍在等用户触发。体检结论要写进回复（扫描范围 + 命中数 + 处理结果），不能只说「已修」。

落点：通用方法论 → 通用技能库；项目专属 → 该项目自带的规则文档；已有同类 → 追加合并，不新建重复。

四条结构缺一不可：

```
现象：可观测事实（数字/报错原文/复现步骤）
根因：机制层面为什么，不是"没注意"
解决：具体做了什么（命令/代码/路径，可直接复用）
防再犯：下次怎么自动避免（判据/检查项/顺序）
```

验收：skill 里能 `grep` 到本次教训关键词；回复给出**完整路径**（独占一行）+ 内容正文；改权威源时同一提交同步生效副本；方案文档追加一行「日期 + 事件 + 固化到哪个 skill」。

**没落地到 skill 的经验 = 没总结**（会随会话压缩丢失）。
